# 成员任务同步与文件交付规范

**版本**：v1.0
**日期**：2026-08-09
**适用对象**：吴、钟、刘、夏及其Codex；若翎的项目统领/集成Codex

## 1. 协作原则

本项目的正式版本只由若翎维护。其他成员可以从GitHub或若翎发送的项目包获取最新上下文，但不向正式仓库提交、推送、创建远端分支或发起拉取请求。

成员的每项任务都在以下独立目录中完成：

```text
handoffs/<成员姓氏>/<任务编号-任务名>/
```

若翎收到交付包后，先独立审查和取舍，再由若翎的项目统领/集成Codex合并、测试、提交和推送。成员交付不直接改变正式项目。

## 2. 唯一同步口令

成员在当前任务对话中确认任务已完成后，只需发送完全一致的口令：

```text
我要同步
```

该口令授权Codex整理和压缩当前任务文件，不授权提交Git、推送GitHub、覆盖核心治理文档或修改其他任务成果。

## 3. 成员Codex收到口令后的动作

Codex必须按顺序执行：

1. 读取当前任务卡，确认任务编号、成员姓氏、对话名称、依据版本、输出目录和验收条件。
2. 只收集本任务产生或明确引用的文件，不默认打包整个项目。
3. 检查文件能否打开、命名是否清楚、来源和验证状态是否完整；不得把计划写成已完成成果。
4. 在任务目录生成或更新 `HANDOFF.md`。
5. 在任务目录生成 `SYNC_PROMPT.md`，供若翎把压缩包交给其Codex时直接使用。
6. 将任务目录压缩为同名ZIP，建议命名为 `<任务编号-任务名>-<成员姓氏>-<日期>.zip`。
7. 向成员报告ZIP的完整路径、包含的文件、已做检查、未验证事项，并明确提示“把ZIP直接发给若翎”。

不得执行：`git commit`、`git push`、创建远端分支、发起拉取请求、合并主分支，或清理成员未提交文件。

## 4. `HANDOFF.md` 必备内容

```markdown
# 任务交付说明

- 任务编号：
- 任务名称：
- 完成人：
- 对话名称：
- 依据的项目版本/日期：
- 交付日期：

## 完成内容

## 文件清单与用途

## 关键结论

## 来源与证据

## 验证方式与结果

## 未验证、局限与待确认事项

## 需要若翎决定的事项

## 建议更新的核心文档
```

## 5. `SYNC_PROMPT.md` 模板

成员Codex根据实际内容填写，不保留尖括号占位符：

```text
若翎现在向你提供一个团队成员的任务交付包。请把当前主项目视为唯一正式版本源，先审查，不要直接覆盖或提交。

任务编号：<任务编号>
任务名称：<任务名称>
交付成员：<姓氏>
成员依据的项目版本/日期：<版本或日期>
交付包：<ZIP文件名>

请按以下顺序处理：
1. 先读取主项目的AGENTS.md、PROJECT_CONTEXT、PROJECT_STATUS、DECISIONS、TASK_BOARD和SYNC_WORKFLOW。
2. 解读交付包中的HANDOFF.md，核对文件清单、来源、验证状态和未确认项。
3. 将内容分为“可合并”“需修改后合并”“暂不采用”三类，并说明理由和可能影响的主项目文件。
4. 检查交付内容是否与当前主项目版本、已确认决策、正式数据状态和其他未提交改动冲突。
5. 先向若翎给出审查结论和建议合并方案；未经若翎确认，不修改主项目、不提交Git、不推送GitHub。
6. 若翎确认后，再实施合并、验证并更新相关核心文档和任务状态。
```

## 6. 若翎接收交付包后的使用方法

1. 把成员发来的ZIP附加到企业转型金融评估主项目中的一个新Codex对话。
2. 打开ZIP内的 `SYNC_PROMPT.md`，将其完整内容作为该对话的第一条任务指令。
3. 让Codex先审查并分类，不立即合并。
4. 若翎根据审查结论决定全部采用、部分采用、要求返工或暂不采用。
5. 确认采用后，再由若翎的集成对话修改正式文件、运行验证、更新 `TASK_BOARD.md`，并提交和推送GitHub。

同一成员可以同时开多个对话，但每个对话必须对应不同任务编号和不同交付目录。新的正式项目版本发布后，成员应在开始下一任务前重新获取最新版本；已经完成的旧交付包不得静默覆盖新版内容。
