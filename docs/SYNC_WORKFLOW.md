# 团队成员简化同步与成果接收流程

**版本**：v2.1
**日期**：2026-08-15
**适用对象**：吴、钟、刘、夏及其Codex；若翎的项目统领/集成Codex

## 1. 协作原则

本项目实行单向GitHub协作。若翎维护的公开个人仓库是唯一正式版本源；吴、钟、刘、夏只获取、clone、pull和读取，不向正式仓库提交、推送、创建分支或发起Pull Request。只有若翎或若翎明确授权的Codex可以修改正式仓库、提交和推送。

成员成果直接发送给若翎即可，不要求任务编号、任务卡、独立目录、固定文件格式或固定同步口令。成员交付不直接改变正式项目，只有经过若翎审查、确认并纳入正式仓库后才成为项目结论。

## 2. 成员开始工作前

### 第一次使用

```text
git clone https://github.com/RuoLing0802/transition-finance-assessment.git
```

### 后续开始新工作

先确认没有未保存的本地改动，再执行：

```text
git pull --ff-only origin main
```

如工作区有未提交改动、分支分叉或同步可能覆盖成果，不得强制拉取、重置或清理；先保留现状并报告给若翎。同步后按 [`CODEX_ONBOARDING.md`](CODEX_ONBOARDING.md) 读取最新版核心文档，再按若翎安排开展工作。

## 3. 成员完成工作后

成员可以直接发送：

- 建议、反馈或分析结论；
- 文档、表格、图片和引用材料；
- 代码片段或软件实现建议；
- 数据盘点、规则研究、评分或测试结果；
- ZIP或其他便于传输的文件。

交付说明至少应让若翎看清：依据的项目版本和日期、完成内容、来源与证据、验证方式、未验证或待确认事项、对MVP或正式文档的影响。成员无需执行任何Git提交或推送操作。

“依据的项目版本”优先填写开始工作时的Git提交短哈希（`git rev-parse --short HEAD`），并可附 `PROJECT_PLAN.md`、`PROJECT_STATUS.md` 的版本和日期。成员本地成果可保存在仓库外，或保存在仓库内自选清楚路径/可选 `handoffs/` 目录；如保存在仓库内，应作为未提交的成员文件保留并直接发送给若翎，不得覆盖核心治理文档或正式代码，下一次拉取前先处理本地改动。

## 4. 可选存档与打包

材料较多、需要长期存档或便于传输时，可自愿使用 [`../handoffs/`](../handoffs/) 目录、`HANDOFF.md`、`SYNC_PROMPT.md` 或ZIP。可选的 `HANDOFF.md` 建议包含：

- 完成人、主题和交付日期；
- 依据的项目版本；
- 完成内容与文件清单；
- 关键结论、来源和证据；
- 验证结果、局限和待确认事项；
- 建议更新的正式文件。

是否使用这些工具由成员和若翎按实际需要决定；没有任务编号、交接文件、ZIP或特定口令，不影响成果交付。

## 5. 若翎与项目总控的接收流程

成员材料由若翎上传到 `01_项目总控与决策`。项目总控必须先审查，不能直接覆盖正式项目：

1. 读取成员材料，确认来源、依据版本和适用范围；
2. 与当前正式项目比较，区分新增、重复、冲突、过时和待确认内容；
3. 给出“建议采纳、部分采纳、暂不采纳”的结论、理由和影响范围；
4. 等若翎确认采用范围后，再修改正式项目；
5. 更新必要的总体计划、状态、决策、数据或其他文件；
6. 完成验证、Git提交、GitHub推送，并确认本地与远端一致。

如果成员成果涉及正式数据、评分体系、MVP范围、技术架构或阶段状态，应同步更新对应治理文档，不能只留在聊天或附件中。

## 6. 数据与开发分流

- 命题方配套模拟数据完成接收登记后，数据盘点、字段审计、质量检查、政策标准、行业规则和评分校准主要在 `03_数据、政策与评分体系` 中进行；独立数据字典、训练/测试划分和正式评分标签仍需另行取得和核验。
- `03` 形成需要长期保留的结论后，由 `01_项目总控与决策` 更新唯一正式总体计划和项目状态。
- 软件开发始终在 `02_软件开发` 中进行，且只有收到完全一致的口令“开始开发MVP”后才允许开始程序开发。
- 当前已取得命题方配套脱敏模拟数据，仅用于比赛开发测试，不是真实企业业务数据；完整“8行业框架＋2行业深验”MVP范围保持不变。
