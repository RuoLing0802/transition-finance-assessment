# 五人团队精简协作机制

**版本**：v1.1
**日期**：2026-08-20
**状态**：精简协作机制已确认
**项目统筹与技术集成**：若翎

## 1. 团队与基本原则

团队共5人：若翎、吴、钟、刘、夏。除若翎继续承担主要软件开发、技术架构和最终集成外，不把任何成员永久绑定为政策、评分、数据、测试或报告负责人。

吴、钟、刘、夏均可根据时间、兴趣和任务需要参与文献政策、行业标准、规则指标、数据治理、软件建议、测试、报告、精益画布、演示和答辩。分工由若翎按实际任务安排；不要求为每项工作建立任务编号、任务卡或固定交接结构。

## 2. 若翎的固定Codex对话

| 对话 | 状态 | 主要职责 |
|---|---|---|
| `00_项目上下文整理与Codex交接包` | 已完成，可归档 | 保留早期上下文整理成果，不再承担日常管理 |
| `01_项目总控与决策` | 当前主对话 | 总体计划、重大决策、项目状态、成员成果审查、正式合并、Git提交与GitHub推送；不承担日常软件编码 |
| `02_软件开发` | M1—M4已正式集成；M5待专项授权 | 程序架构、前后端、数据库、测试、桌面封装和部署；每个新开发阶段仍须收到完全一致的口令“开始开发MVP”后实施 |
| `03_数据、政策与评分体系` | 政策规则阶段成果已到达，继续规范化 | 正式参赛数据导入与审计、政策标准、行业规则、指标体系和评分校准；当前优先统一来源ID、证据路径和规则角色，长期结论交由 `01` 更新正式文件 |
| `04_报告、PPT与答辩` | 暂不创建 | 等程序、数据和评分体系基本稳定后再建立 |

固定对话是长期职责分区，不代表自动调用子Agent，也不要求成员按任务编号创建对话。

## 3. 成员分工与开始工作

1. 成员第一次使用时，通过公开地址clone若翎维护的正式仓库。
2. 每次开始新工作前，先确认没有未保存的本地改动，再执行 `git pull --ff-only origin main`。如存在本地改动或分叉，先保留并报告，不得覆盖。
3. 读取 `AGENTS.md`、`README.md`、`docs/PROJECT_CONTEXT.md`、`docs/PROJECT_STATUS.md`、`docs/PROJECT_PLAN.md`、`docs/DECISIONS.md`、`docs/DATA_STATUS.md` 和本文件。
4. 按若翎安排确认目标、输入、期望成果、来源要求和验收方式；不自行扩大项目范围。
5. [`TASK_BOARD.md`](TASK_BOARD.md)可用于记录重要待办，但不是任务启动前置条件。

## 4. 成员成果交付

成员完成工作后，可把以下任一形式直接发送给若翎：

- 分析、建议和反馈消息；
- 文档、表格、图片或其他材料；
- 代码片段或软件实现建议；
- 数据盘点、审计或测试结果；
- ZIP或其他便于传输的文件包。

项目内需要长期保留的成员原始成果统一优先放入[`../团队成果/`](../团队成果/)并按“成员/模块或主题”归类；这只是存档约定，不是交付前置条件。成员成果仍须经01审查后才成为正式结论。

交付时应说明依据的项目版本、完成内容、来源与证据、已验证和未验证事项、风险以及需要若翎决定的问题。任务编号、固定目录、`HANDOFF.md`、`SYNC_PROMPT.md`、固定ZIP结构和“我要同步”口令均为可选工具，不是交付必要条件。成员不向GitHub提交、推送、创建分支或Pull Request。

“依据的项目版本”优先填写开始工作时的Git提交短哈希（可用 `git rev-parse --short HEAD` 查看），并可附 `PROJECT_PLAN.md`、`PROJECT_STATUS.md` 的版本和日期。成员本地成果可保存在仓库外，或保存在仓库内自选的清楚路径/可选 `handoffs/` 目录；仓库内成果视为未提交的成员文件，不得覆盖核心治理文档或正式代码，发送给若翎前后都应自行保留，下一次拉取前先处理这些本地改动。

## 5. 项目总控接收与合并

若翎把成员材料上传到 `01_项目总控与决策` 后，项目总控按以下顺序处理：

1. 读取材料并确认来源、依据版本和适用范围；
2. 与当前正式项目比较，区分新增、重复、冲突、过时和待确认内容；
3. 给出“建议采纳、部分采纳、暂不采纳”的审查结论；
4. 等若翎确认后再修改正式项目；
5. 完成必要的文档更新、验证、Git提交和GitHub推送。

`PROJECT_CONTEXT.md`、`PROJECT_STATUS.md`、`DECISIONS.md` 和 `PROJECT_PLAN.md` 由 `01` 维护。成员提交的成果在若翎确认并纳入正式仓库前，不视为正式项目结论。

## 6. 子Agent规则

- 默认不启用子Agent，也不因为固定对话分工而自动启用。
- 只有若翎明确要求，或任务明显适合并行只读分析时，才可调用子Agent，例如大规模文献检索、政策资料归纳、代码只读检查、测试结果分析和多方案比较。
- 正式代码和核心项目文件原则上由当前主对话统一写入，避免并行修改冲突。

## 7. 必须由若翎确认的事项

- MVP范围、“8行业框架＋2行业深验”和第二深验行业；
- 技术栈、模块边界、公共接口、数据库、部署和发布方式；
- 规则、因子、模型、权重、阈值和行业基准进入系统的最终版本；
- 多人修改的合并、测试通过、演示版本冻结和最终提交包。

所有成员都可以提出替代方案和风险，但不得仅在个人对话中静默改变这些项目级决策。
