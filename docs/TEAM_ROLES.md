# 五人团队动态协作与交付机制

**版本**：v0.4
**日期**：2026-08-09
**状态**：动态任务制已确认
**项目统筹与技术集成**：若翎

## 1. 团队与基本原则

团队共5人：若翎、吴、钟、刘、夏。除若翎继续承担主要软件开发、技术架构和最终集成外，不把任何成员永久绑定为政策、评分、数据、测试或报告负责人。

吴、钟、刘、夏均可根据时间、兴趣和任务需要参与文献政策、行业标准、规则指标、数据治理、软件辅助、测试、报告、精益画布、演示和答辩。分工以具体任务卡为准，同一成员可以同时参与多个工作方向，同一任务也可以有多名协作者。

## 2. 按任务分工，不按姓名分工

每项任务必须先登记在 [`TASK_BOARD.md`](TASK_BOARD.md)，至少明确：

- 任务编号与单一成果目标；
- 当前负责人、协作者和复核人；
- 依据的项目版本与输入材料；
- 允许修改的文件或独立输出目录；
- 交付格式、验收条件、依赖和截止时间；
- 当前状态：待认领、进行中、待复核、已完成或阻塞。

任务负责人只表示对该项交付负责，不代表长期岗位。任务结束后可以重新分配下一项工作。

## 3. 同一项目中的多对话工作法

- 一个明确成果对应一个Codex对话，例如“铜产业政策标准卡”“100分评分框架审查”“数据字典草案”“MVP文件上传模块”“竞赛报告大纲”。
- 对话标题统一使用：`[任务编号] 成果名称 - 成员姓氏`。
- 所有对话都从同一项目根目录启动，并读取同一套 `AGENTS.md`、项目上下文、状态、决策和任务台账。
- 纯分析、资料整理或写入各自独立交付目录的任务，可以在普通对话中并行进行。
- 吴、钟、刘、夏的对话不直接修改核心治理文档或若翎的正式开发代码，统一在各自的 `handoffs/` 任务目录中产出研究稿、建议稿、测试结果或代码辅助文件。
- 成员之间无需管理分支、worktree或拉取请求；若翎自己的并行开发对话可按需要使用worktree，最终仍由若翎的集成对话统一取舍和合并。
- `PROJECT_CONTEXT.md`、`PROJECT_STATUS.md`、`DECISIONS.md`、`PROJECT_PLAN.md` 和 `TASK_BOARD.md` 属于核心治理文档，成员可提出更新建议，但原则上由若翎的项目统领对话统一合并。

## 4. 建议的任务类型

| 类型 | 编号前缀 | 典型成果 | 可由谁承担 |
|---|---|---|---|
| 政策、标准与文献 | `RES` | 标准条款卡、文献综述、行业政策证据 | 任意成员 |
| 规则、指标与金融逻辑 | `RULE` | 评分规则、阈值依据、边界案例 | 任意成员 |
| 数据与治理 | `DATA` | 数据字典、字段映射、质量规则、数据审计 | 任意成员 |
| 软件与技术实现 | `DEV` | 代码、接口、架构、部署、技术验证 | 若翎主导，其他成员可辅助 |
| 测试与验证 | `TEST` | 测试矩阵、金标准案例、验收记录 | 任意成员 |
| 报告与展示 | `DOC` | 报告、精益画布、PPT、演示和答辩材料 | 任意成员 |
| 项目统筹 | `PM` | 任务拆分、状态更新、版本整合、最终决策 | 若翎主导 |

## 5. 开始任务时

成员Codex必须：

1. 按根目录 `AGENTS.md` 检查本地版本和远端/更新包状态；
2. 读取 `PROJECT_CONTEXT.md`、`PROJECT_STATUS.md`、`DECISIONS.md`、`TASK_BOARD.md` 和本文件；
3. 确认当前任务编号、目标、负责人、输入、输出路径和验收条件；
4. 报告会修改哪些文件，确认不会覆盖其他正在进行的任务；
5. 若任务尚未登记，只创建或建议任务卡，不自行扩大项目范围。

## 6. 完成任务与“我要同步”

每项交付必须附一份 `HANDOFF.md`，至少包括：

- 任务编号、成员、对话名称和依据的项目版本；
- 完成内容、文件清单、关键结论和验证方式；
- 来源与证据、未确认项、局限和需要若翎决策的事项；
- 是否建议更新核心治理文档；
- 交付包路径，以及压缩包包含内容的核对结果。

不使用Git时，统一保存到：

```text
handoffs/<成员姓氏>/<任务编号-任务名>/
```

任务完成后，成员向当前Codex发送完全一致的口令：

```text
我要同步
```

Codex随后自动完成四件事：检查本任务输出、补齐 `HANDOFF.md`、生成供若翎Codex直接使用的 `SYNC_PROMPT.md`、将任务目录压缩为ZIP。成员只需把ZIP文件发给若翎，不需要执行提交、推送、分支或拉取请求。详细规范见 [`SYNC_WORKFLOW.md`](SYNC_WORKFLOW.md)。

若翎的集成对话先审查交付包，列出“可合并、需修改、不采用”三类结论；只有若翎确认后，才修改主项目并由若翎的Codex提交、推送GitHub。

## 7. 必须由若翎确认的事项

- MVP范围、“8行业框架＋2行业深验”和第二深验行业；
- 技术栈、模块边界、公共接口、数据库、部署和发布方式；
- 规则、因子、模型、权重、阈值和行业基准进入系统的最终版本；
- 多人修改的合并、测试通过、演示版本冻结和最终提交包。

所有成员都可以提出替代方案和风险，但不得仅在个人对话中静默改变这些项目级决策。
